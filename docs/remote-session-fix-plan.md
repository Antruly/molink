# moLink 0.11.0：远控卡顿、切换和跨版本修复清单

基线：`/home/zwy/mintSet/public/molink`，`56b8df9`（0.11.0 及后续 CI 提交）。不以 `cursor/molink` 的 0.9.63 工作树为基线。下文的根因基于源码和单测分析，尚未做新旧版本真机对测。

## 第一批已实现

- Web 在前台点对点会话视频无响应时主动发起探测；普通控制响应不能代替视频响应，静止桌面的空帧仍算有效响应。持续缺关键帧或探测超时后，用已有会话令牌尝试仅中继重连。Core 也会上报会话建立后的 ICE 失败，不再只依赖会话建立阶段的回调。
- 出站设备 ID 会话可通过已有界面的「强制中继」，或在启动控制端 core 时设置 `MOLINK_RELAY_ONLY=1` 来跳过 ICE 和局域网直连。仅中继沿用原中继协商；具体协议由双方可用的中继端点决定。
- Web 下载只有在偏移、总字节数以及结束通知都匹配后才保存；未完整接收在 30 秒无进展后报错。Windows 原生端已有结束通知和长度的完成检查，本批补了块长度边界检查。Web 的视频推送现在也受应用内会话前后台状态控制。
- 新增前端下载回归：`node --test frontend/tests/download-state.test.mjs`。尚未交付双端协商切换、队列满后的服务端文件重试、独立文件通道和跨版本真机验证。

## 第二批已实现

- 主机的下载队列拒绝文件块时，保存原请求、偏移和数据，每 100 毫秒重试，最多等待 20 秒；取消和会话关闭会清理待重试请求。旧客户端不需要再次发送 `pull`。上传的 `complete` 先于最后一块到达时，主机等待并校验完整字节数；超时删除临时文件并返回失败。
- 已从中继升级的会话在中继断开后拒绝文件块，不把文件悄悄改走无重传的点对点链路。Windows 原生端收到失败的下载结束消息时删除部分文件，长期无进展时也会取消。直接以点对点建立的旧流程未改变。
- Web 收到从中继切到点对点的通知时保留当前显示，请求新的关键帧，并丢弃旧路径上仍在排队或解压的帧。重连时旧连接的解码和 WebRTC 回调不能再更新当前会话。流视频有缺帧导致参考链断开时，也会启动已有的关键帧超时检测。
- 双端协商切换、独立可靠文件流和跨版本真机对测仍待完成。当前 Web 的路径通知只能防止已排队的旧帧覆盖新画面，不能识别切换后才到达的所有旧路径帧；这需要双方支持画面代际。

## 第三批已实现

- 切到点对点之后，仍接收当前会话中继路径上的文本控制消息。两端 ICE 完成时间不同，以及切换前已排队的输入、鉴权、文件结束通知都不会再被路径过滤丢弃。发送仍只选一条路径，不增加双投。旧端修复请求的空格和字段顺序不再影响路由，JSON 解析和鉴权继续由会话层完成。
- 视频队列满时拒绝新的增量帧，把失败反馈给已有的重建流程，不再静默删除已接受的参考帧。新关键帧仍会替换队列中的旧画面。
- WebSocket 中继的待完成写入窗口由 8 MiB 收紧为 1 MiB，普通视频/文件最多使用其中 768 KiB，为控制和音频保留空间。合法大视频帧在没有在途写入时可单独发送，修复超过旧 8 MiB 上限的完整画面永远卡在队首的问题。单张大帧仍可能阻塞同一 TCP，独立流与分片调度仍待实现。
- 新增非同步双端切换、带空格的旧消息、视频参考链保留及中继写入额度回归。此批不改变协议格式，也没有完成 `path_switch_v2` 双端协商或真实弱网/跨版本验证。

## 先做什么

1. 有“连接开始正常，随后卡死”的用户：Web 端用同一目标、同一画质分别测“自动”和“强制中继（不打洞）”。同一个版本也可能有多种问题；强制中继显著改善才优先查点对点路径。两者都慢则继续测采集、排队和解码。重复观察至少一次路径变化，不能只看平均帧率。
2. 首个修复提交做 **P0-1 的止血和超时恢复**；不等新切换协议设计完成。文件传输的提前结束是独立问题，可同时拆成单独提交 **P0-2**。
3. 跨版本默认用现有可靠路径和能力交集兜底，通过双向矩阵再启用新切换行为。随后做 P1 的队列和前后台优化。

## P0-1：点对点升级没有可恢复的会话状态

**已确认的代码路径：** `backend/src/p2p/p2p_manager.cpp` 的 `deliver_outgoing` / `deliver_incoming` 各自在本地 ICE（点对点连通性检查）完成时切换，并移除连接尝试记录。两端没有应用层确认“对方已准备接收”。`backend/src/transport/switchable_transport.cpp` 的 `set_ice` 直接换 `active_`；`wire` 过滤旧路径上的大部分消息，活跃路径关闭则结束会话，没有会话内降级。后续 ICE 状态变化仍由尝试阶段回调处理时，记录已移除，`finish_*` 找不到它；`juice_transport::is_open` 变为 false 也不会自动等价于通知上层关闭。`connect_proxy::on_ready` 的切换通知只更新 UI 路径，接收端没有因为该通知建立新画面基准。这个组合能解释切换附近丢控制/丢增量、点对点失联后窗口还像连接着；实际占多少故障需日志验证。

**第一提交：止血，不改协议。** 在 `p2p_manager` 的两侧统一加策略开关：兼容或故障模式保留可靠中继，禁止会话中途升级；涉及硬性只中继的入口，应在建立阶段也禁止 ICE 先赢，不能只跳过 `set_ice`。`ice_agent`/`juice_transport` 增加交付后的状态订阅，在所属事件循环通知活跃传输（使用弱引用，保证只通知一次，析构时解除订阅；不要覆盖还在协商时的状态处理）。旧对端或后备中继未经验证时，明确关闭故障链路，复用已有会话令牌走一次可靠路径重连；避免本端偷偷切回中继而对方仍过滤中继控制包。Web 端已有 `relay=only`，原生端确认重试实际走了可靠路径，而不是只改标签。重连有代际保护和退避；鉴权错误/用户主动断开走原有流程，不触发网络兜底。

**补齐视频无进展检测。** `frontend/src/lib/client.ts` 的 `noteMissingStreamKeyframe` 由流增量到达触发，且没有当前路径判定；零视频包、瓦片卡住时都不靠该函数恢复。现有 `requestFrame` 超时只覆盖拉取，推送开启时直接返回；通用入站监听也不能把持续收到 `pong` 视为画面正常。修改 `case 'transport'` 和 `welcome`，保存当前路径；在已认证、前台且确实期待画面的会话中区分最后收到画面、最后成功提交画面、等待关键帧起点。计时器按连接代际取消：先请求一次修复；持续失败且当前为 `p2p` 才固定中继重连。推送静态瓦片允许没有新图，使用空帧/拉取探测判断是否仍响应，不以静止桌面触发重连。原生消费同一 core 的失败通知，检查是否需要对应的画面进展检测。

**后续提交：双端协商切换。** 只有双方声明 `path_switch_v2` 才发新消息；通过现有可靠通道交换候选路径及代际，用候选通道做双向探测，确认对端能接收后才能提交。准备阶段旧路径仍接收控制；切换/回退有超时，收敛到同一路径，并用新画面代际拒绝迟到旧帧。提交后主持端给当前会话安排干净的关键帧或完整瓦片基准；接收端先保留最后一张图，等新基准可显示才替换。控制消息避免双投后重复执行；文件不随着画面改道。后备中继半开或已关闭时走重连而不是死等。

**验收：** 扩展 `backend/tests/switchable_transport_test.cpp`，覆盖两端先后完成、准备超时、活跃 ICE 关闭、切换中可靠路径关闭、迟到回调，以及旧版不升级。端到端分别测视频无包但仍有 pong、只有增量、静止桌面、拔网再恢复。记录 `path_from/to`、原因、连接代际和首张可显示画面的耗时，不记录验证码或令牌。

## P0-2：文件控制消息与文件块可能乱序，流量拒绝后可能停住

**已确认的代码路径：** `backend/src/file_transfer.cpp::pull` 最后一块入队后立即发 `eof`，并删除下载状态。`backend/src/transport/relay_transport.cpp` 使用 `channel_scheduler::drain`，其中控制优先于文件；点对点升级后 `switchable_transport` 还会让文件字节走中继而 JSON 控制走活跃路径。两种情况下，`eof` 都可能比最后一块先到。`frontend/src/components/FileTransferPanel.tsx` 在 `case 'eof'` 直接拼 Blob 并清理下载，未校验收到的字节数；可能提前保存截断文件。文件块入队失败时服务端倒回偏移后返回，但客户端正常是收一块才发下一条 `pull`；现有重试单测手工发下一次 `pull`，不代表真实客户端会重试。上传端也不能把调用 `sendFileChunk` 视作远端已接受。

**第一提交：** Web 下载维护 `nextExpectedOffset` 和 `eofSeen`；校验 `id`、连续偏移和总长度。只有 `received == size && eofSeen && ok !== false` 才保存；`eof` 先到就继续等最后的在途块，超时明确失败，保留零字节文件成功分支。核对 `clipboard-sync.ts` 和 Windows `session_client.cpp` 中的文件完成逻辑，使用相同字节数约束；上传的 `complete` 也必须等接收端验证最后一块，不能依赖 UI 已发送进度。

**第二提交：** `file_transfer` 对旧 peer 保留一次待处理 `pull`，入队拒绝后等传输可写或有界重试，按原 `id`/偏移发送；取消、会话关闭、超时统一清理。不要让旧客户端定时盲发无偏移的 `pull`，否则“原块仍在途”时会多推进一块。支持新版时，再协商带 `offset` 的拉取/确认与幂等重发。若可靠文件路径失效，暂停或明确取消，不能静默改走没有重传的 ICE 分片。上传提供者收到接收端确认或协商过的额度后才继续窗口推进。

**验收：** 模拟 `eof` 先到、最后一块延迟、偏移重复、短文件、空文件、慢接收和中继关闭。测试通过实际回调恢复拒绝的 `pull`，而不是在测试里额外补发。下载及上传最终逐字节或 SHA-256 校验；失败不得保存为成功。

## P1-1：UDP 大帧丢片与发送突发会一起拖慢视频和控制

**已确认的实现限制：** `backend/src/transport/juice_transport.cpp::send_message` 把大包按每片约 1190 字节拆分，在调用内一次发送完；`handle_datagram` 需全部片到齐才交付，无重传。256 KiB 一帧约 221 片；一片丢失就丢整帧，关键帧丢失还会拖累依赖它的增量帧。0.10.6 把修复和关键帧移回 ICE，解决旧中继吞掉修复的问题，但没有让 UDP 可靠；独立 AV1 帧也仍有条件走中继，不能假设所有视频都同路。

**改法：** 首先记录每帧字节/分片数、发送耗时、重组完成/过期及关键帧等待。`juice_transport` 给分片发送设每 tick 字节预算，给发送队列和重组队列设时间及字节上限；同一路径优先低延迟控制。舍弃视频时以参考链为单位，丢增量后清掉依赖项并触发限频重建，不可继续发大量不可解增量。旧版不支持新分片/可靠修复机制时保持原格式；弱网先选择可靠视频路径，比单独调大 Web 乱序等待时间更直接。后续如新增可靠关键帧通道，必须明确同一视频代际的顺序与交付确认，不能把 0.10.6 前的无健康检查双路行为搬回来。

## P1-2：单条中继 TCP 上的队列无法保证输入低延迟

**已确认的代码路径：** `backend/src/transport/relay_transport.cpp` 把数据交给 WebSocket 写队列，`relay_transport.h` 限制 8 MiB 在途；`channel_scheduler` 的优先级只影响尚未交给 WebSocket 的消息，已排入同一 TCP 连接的文件/视频挡在控制前面。队列有上限不等于等待时间有上限。`channel_scheduler::evict_video_for` 按字节压力逐个丢非关键帧，现有 `keyframe` 标记不足以判断后面哪些流帧依赖被丢的帧。

**改法：** 给 `drain` 补充每轮字节额度和每类最大队龄；按实际吞吐动态收紧共享路径的文件写入窗口，留出控制额度，限制单次文件写入批量。流视频按代际丢弃并触发重建，瓦片按基准/修复规则处理。保留可发送单张大关键帧的边界测试，同时为超过底层可发送上限的帧设置降尺寸或明确失败，不能在队首无限重试。排队年龄仍不达标时，把文件移到独立可靠流并经能力协商启用；同一 TCP 内提高优先级不能消除已经发生的阻塞。验收：限速下同时传文件、拖窗、敲键，单独记录控制往返 p95、提交画面的帧龄、文件吞吐；阈值由团队在固定网络配置下设定，不能只测平均 FPS。

## P1-3：切换远控标签与切换视频模式分开查

**标签切换：** `frontend/src/lib/session-connection.ts::setForeground` 管全速/后台拉取；`client.ts::watchVisibility` 判断的是整个文档可见，`requestFrame` 在推送时直接返回。应用内切标签时文档仍可见，旧会话可能继续推送和解码；是否是现场主因要同时开两个会话实测。把 `video-push` 统一由「能力支持、连接可用、文档可见、会话前台」共同决定，四个状态任一变化都重算。旧版继续低频拉取，不在每次切标签强制关键帧；沿用保存的画面，只有参考链缺失才请求恢复。验收：来回切换两个连接，检查后台收到/解码帧数和回前台首帧时间，同时检查剪贴板作用对象仍是前台会话。

**视频模式：** 0.11.0 删除自动混合模式，默认瓦片，并将旧设置 `mixed` 迁移为 `tiles`。这不解决网络路径切换，也不代表瓦片适用于滚动/视频：若同设置下升级后变慢，先检查实际模式与编码器。新端兼容读取旧 `video_mode`，未知/缺失值走明确默认；旧端没有能力声明时用其已支持的瓦片/拉取路径。保留用户明确选择的 `stream`，取真实编码能力与实际解码能力交集；没有交集时回落瓦片并让 UI 表示实际选择。Win7 如果两种网络都慢，先对照 `CHANGELOG.md` 的 GDI 信息（旧 VM 的 BitBlt 曾约 55 ms，不是本次实测），分别测采集、编码、网络排队和解码后再调码率。另一个待测小项：`client.ts::noteFrameLuma` 在视频绘制路径同步读 Canvas 像素，用性能录制确认后再考虑仅诊断开启时低频采样。

## 版本兼容发布门槛

- 0.10.5 → 0.10.6 的主要变化是修复包路由、Web 解码乱序保护和仅中继重连；0.10.6 → 0.11.0 的会话相关差异集中在视频模式与原生令牌重连，不等同于增加 ICE 双边切换协议。可用 `git diff --stat v0.10.6 v0.11.0 -- backend/src frontend/src shell/windows` 复核。
- 按**双方能力**决策，不按版本字符串猜：`hello`/`welcome` 可选字段缺失按旧端处理；保留既有 MOLK 二进制封包和旧 `mode` 字段。接收旧版经中继发出的关键帧、瓦片修复、时钟和修复请求。修复请求如涉及跨路过滤，按 JSON `type` 匹配，而不是依赖字符串恰好没有空格；测试带空格和不同字段顺序的旧消息。
- 必测：`0.11.0 × 0.11.0`、`0.10.6 × 0.11.0`、`0.10.5 × 0.11.0`；版本互换控制端/被控端。发补丁时再让候选构建分别和上述版本双向组合。每组至少跑 Web 与原生的控制/被控组合，先可靠路径，再自动路径；覆盖首帧、输入、静态/运动、重连、标签切换、剪贴板、文件完整性。远端浏览器直连和本地 core 代理要分开记录；若仍承诺支持 0.9.x，额外用实际发布包双向验证，未测不能宣称全版本兼容。
- 测一次性验证码：新原生端收到 `welcome.session_token` 后重连带 `hello.session`；旧主机未发 token、主机重启使其失效、旧原生端不会续用 token 时，应提示重新获取验证码/审批，而不是无限用耗尽码重试。单独验手动断开不被旧连接回调重新打开。
- Win7 安装兼容与协议兼容分开发布：Win7 SP1（含 x64 系统）用官方 x86 原生包；常规 x64 安装器最低 Windows 8。分别跑安装与启动、画面加输入，不把能安装当成能互连。
