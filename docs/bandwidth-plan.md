# 带宽峰值优化计划

当前 `0.5.0` 已经具备：瓦片增量、条带合并、zlib 自适应、RGB565 有损“流畅”档、
画质预设与客户端自适应。静态画面带宽很低；峰值主要出现在窗口拖动、网页滚动、
视频播放、全屏切换等大面积连续变化时。

本文件是后续优化的实施顺序，不改变现有协议的前提下优先做前三项。

## 先量化

每次改动前后用 `tools/bench_quality.py` 和 `/api/info` 的 `capture` 统计对比：

- 关键帧字节数、增量帧字节数
- 每秒线速帧数与实际绘制帧数
- 编码耗时（目标：关键帧 ≤ 1 帧预算，增量帧 ≤ 1 帧预算）
- 带宽 p95 / 峰值，而不只是平均值

建议在 `/api/info` 增加每帧 `tiles`、`bytes`、`encode_ms` 的滚动统计，便于定位
“大面积变化”还是“大量小变化”。

## 1. 二维脏矩形合并（优先）

现在 `build_changed_tiles()` 只在同一行内把连续变化瓦片合并成水平条带。大面积
变化时仍会产生较多条带、表项和独立 zlib 流。

做法：

1. 先按行找出变化条带；
2. 若相邻两行的条带在水平方向重叠或间距不超过 1 个瓦片，就合并为一个矩形；
3. 矩形高度达到阈值（例如 2–8 个瓦片）后停止增长，避免单个矩形过大；
4. 对每个矩形单独构建瓦片 blob 和 zlib 流。

收益：减少表项与 zlib 流数量，提高跨行压缩率；不改变客户端解码路径。
验收：文档滚动、IDE 编辑、窗口拖动场景下带宽峰值下降 ≥ 30%，解码路径不变。

## 2. 大面积变化的有损兜底

“流畅”档已有 RGB565。对合并后面积超过屏幕 15%–20% 的矩形，再增加一档
空间降采样兜底：

- 2×2 平均后按原尺寸复制回瓦片（解码端无需新 codec）；
- 或直接使用 RGB565 + 更低 zlib 级别；
- 阈值触发，不影响小范围文字/控件更新。

验收：全屏切换、视频播放时峰值带宽下降 ≥ 40%，文字仍可读。
不要默认对所有内容降采样；只在“大面积 + 高频变化”时触发。

## 3. 大帧时间整形

单帧压缩后仍超过阈值（例如 1 MiB）时，不要一次塞进一个 WebSocket 消息：

- 按矩形/条带拆成多个传输单元；
- 利用现有 `request-frame` 拉取模型，在多个拉取周期内交错发送；
- 客户端仍按顺序合成，画面完整时间略微增加，但峰值被摊平；
- 若队列积压超过 N 帧，直接跳到最新关键帧，避免“越拖越慢”。

验收：峰值带宽不超过目标码率的 1.5 倍，交互延迟不增加。

## 4. 选择性编码（中期）

按区域内容选择编码器，而不是全局替换 zlib：

- 文字/UI：保持 BGRA + zlib（无损）；
- 大面积一次性图像：JPEG（libjpeg-turbo 编码，浏览器 `createImageBitmap` 解码）；
- 持续动态视频：仅在双方都有硬件 AV1/H.264 编码时启用，软件 AV1 不作为实时路径；
- 新增 codec 时必须同时提供浏览器端解码回退，未知 codec 保持上一帧。

## 5. 自适应策略

当前“自适应”用 RTT、拉帧完成率和吞吐量切换预设。补充：

- 用最近 2 秒的“实际绘制帧率 / 目标帧率”判断拥塞；
- 大面积变化时优先降到“流畅”，而不是只降采集帧率；
- 记录每次切换的原因，便于现场排查。

## 暂不做

- 用软件 AV1/SVT-AV1 做实时编码：延迟和 CPU 成本不可接受；
- 为省字节而关闭关键帧：会放大丢包/重连恢复时间；
- 用 Brotli 替代 zlib：浏览器需要额外 WASM 解码器，首帧延迟更高。
